# Handover — 2026-08-10

## Goal
Dhanu asked to build "LuxLibrary OS" — a premium personal-library operating system for a 2,000+ book collector, from an extensive spec (11-phase build: dashboard, catalog, AI librarian, collections, analytics, reading tracker, etc.). Work proceeded: marketing home page first, then "the Operation site" (the actual app), then iteratively via bare "next" / "next 5" prompts to build out the full IA one module (or batch) at a time, then "confirm and do it" to provision a real database and migrate pages off mock data one at a time, then finished that migration, then made Add Book actually persist, then added book edit/delete (all same day, across several back-to-back sessions).

## State
- Marketing site (`/`) and the full app shell (sidebar covering every IA section, topbar with search + Add Book) are built and deployed.
- **20 screens exist.** Only **Profile** is still unbuilt (falls through to the generic `app/(os)/[section]/page.tsx` "not built yet" page).
- **A real Neon Postgres database is live and seeded**: 28 books, 18 authors, 8 publishers, 7 genres, 2 series, 7 shelves, 6 notes, 13 quotes — the same content the mock data always showed, now persisted for real.
- **Every screen now reads from the real database.** `lib/mock-data.ts`'s `MOCK_BOOKS` and `MOCK_NOTES` are no longer imported by any page — only by `prisma/seed.ts`. This session migrated the last five: Dashboard, Analytics, Reading Life, Timeline, Notes.
- No auth (single-owner app, deliberately not built).
- **Add Book, Edit, and Delete all actually persist now.** Add creates a real `Book` row (plus `Author`/`Genre` upserts); Edit (on Book Detail) updates title/author/genre/format/status/rating; Delete (two-step confirm on Book Detail) removes the row and redirects to Library. All three live in `lib/book-actions.ts` and revalidate the whole app.
- No CSV/import pipeline, no real LLM behind AI Librarian (rule-based pattern matching over real data, clearly labeled as such in the UI, not hidden as if it were a live model).
- Production: **https://luxlibrary-os.vercel.app** — Vercel project `dkns/luxlibrary-os`, auto-deploys on push to `master`. GitHub: `khdanushka-spec/luxlibrary-os` (public).

## Key decisions
- **Mock data first, database later, page by page.** Every module was built against a shared `lib/mock-data.ts` dataset before any database existed, then migrated to Prisma incrementally (Library+Detail together, then 6 aggregation pages, then Quotes+Search, then AI Librarian, then Dashboard/Analytics/Reading Life/Timeline/Notes — the last batch) rather than provisioning a DB up front or converting everything at once. Every intermediate state stayed shippable, and each migration step was verified against numbers already known from the mock-data era — a real bug (see Gotchas) was caught this way.
- **Dashboard's "curated" content (today's pick, AI insights, favorite genres/authors) is now computed live from real book data, not fixed mock strings** — new `lib/dashboard.ts` (`getTodaysPick`, `getAiInsights`), plus new aggregate queries in `lib/db-books.ts` (`getDashboardStatsFromDb`, `getCollectionValueFromDb`, `getRecentlyAddedFromDb`, `getTopGenresFromDb`, `getTopAuthorsFromDb`, `getNotesFromDb`). Same rule-based-but-real philosophy as AI Librarian. `lib/analytics.ts`'s `getAnalytics()` now takes `(books, totalValue, avgValue)` — the value figures come from a real `purchasePrice` Prisma aggregate instead of `getBookDetail()`, closing the Analytics gotcha called out in the previous handover. `lib/reading.ts` and `lib/timeline.ts` now take `books`/`notes` as parameters instead of importing mock data directly, following the pattern `lib/collections.ts`/`lib/publishers.ts` already used. Reading streak (`MOCK_STATS.readingStreakDays`) stays mock-sourced deliberately — there's no `ReadingSession` data to derive a real streak from.
- **New DB-backed pages must set `export const dynamic = "force-dynamic"`** or Next statically renders them once at build time using whatever was in the database during `next build`, then never refreshes — caught when a first build showed Dashboard/Analytics/Reading/Timeline/Notes as `○ (Static)` instead of `ƒ (Dynamic)` like every other DB page. All five now have it.
- **All three book mutations (`lib/book-actions.ts`'s `addBook`/`updateBook`/`deleteBook`) call `revalidatePath("/", "layout")`** rather than listing every individual route that shows book counts (Library, Dashboard, Analytics, Wishlist, Authors, Genres, Reading, Collections...) — simpler and correct for a single-owner app with no meaningful traffic cost to a full-app revalidation. The Add Book dialog's genre/format/status `<select>`s were previously uncontrolled (no `value`/`onChange`) and silently ignored on submit even during the mock-only era — now controlled state, actually sent to the action.
- **Editing a book's author/genre re-links via delete-then-recreate, not update-in-place.** `updateBook` deletes the book's existing `BookContributor`/`BookGenre` rows, then creates fresh ones against the (possibly new, possibly upserted-existing) author/genre — needed because those are composite-PK join rows keyed on the old author/genre id, not a field that can be reassigned. Renaming an author this way does **not** clean up the old `Author`/`Genre` row if it's now orphaned (0 books) — left as-is deliberately, since every page that lists authors/genres derives its list from `getAllBooksFromDb()`'s book-author relations, not the `Author`/`Genre` tables directly, so an orphaned row is invisible everywhere in the UI and costs nothing to leave.
- **Delete uses a two-click same-button confirm** (`components/library/delete-book-button.tsx`: "Delete" → click → "Confirm delete?" → click → deletes), not a separate modal, and resets back to the unarmed state on blur — no `window.confirm()` (blocks the event loop and looks out of place in this UI) and no extra dialog component for a single destructive action.
- **Migrating a page to the database means adapting Prisma rows into the existing `MockBook` shape** (`lib/db-books.ts`'s `toMockBook()`), not rewriting consuming components — `BookCard`, `BookListRow`, `LibraryView`, etc. never changed; only what a page fetched from did.
- **Library and Book Detail were migrated together, not one at a time**, because they're linked by id — wiring one to real DB ids while the other still looked up the old mock "1".."28" ids would have made every click-through 404.
- **shadcn/ui here is built on Base UI, not Radix.** Components take a `render` prop instead of `asChild` (e.g. `<Button render={<a href="/x" />}>`), and a non-`<button>` render target needs `nativeButton={false}` or Base UI logs a console error.
- **Prisma 7 moved connection config out of `schema.prisma`** into `prisma.config.ts`, and `PrismaClient` now requires an explicit driver `adapter` (`@prisma/adapter-neon` here) — a real API break from what most training data assumes. `prisma.config.ts` reads `process.env.DATABASE_URL` directly, not the throwing `env()` helper, so `prisma generate` survives a build before any database exists.

Exports `hashCode` for reuse elsewhere (still used for cover-gradient seeding and reading-progress/date placeholders, which have no real data source). Never call this for a real field that now has a DB column (publisher/shelf/isbn/summary/quote/purchasePrice) — see Gotchas.

- `app/(os)/ai/actions.ts` and `lib/book-actions.ts` — the Server Actions in the app (`askLibrarian`, and `addBook`/`updateBook`/`deleteBook`). All `"use server"` files called from client components that can't reach Prisma directly. Follow this pattern for any future client-interactive DB write.
- `components/library/edit-book-dialog.tsx`, `components/library/delete-book-button.tsx` — the Book Detail page's mutation UI. Both client components; `EditBookDialog` receives the current book's fields as props from the server-rendered page rather than fetching them itself.

## Gotchas / constraints learned
- **The single biggest recurring bug class in this build**: `lib/book-detail.ts`'s `getBookDetail(book)` derives publisher/shelf/ISBN/summary/favorite-quote/purchasePrice from a hash of `book.id`. Fine for `MOCK_BOOKS` (stable "1".."28" ids), **silently wrong** for a database book (a real cuid the hash was never seeded against). Publishers, Quotes, Search, AI Librarian, and (this session) Analytics all hit this and needed a real fix — query the actually-stored field — not just a data-source swap. **As of this session, every page is migrated, so nothing in `app/` calls `getBookDetail()` on a DB book anymore** — but if any future feature needs a book field, check the Prisma schema for a real column before reaching for this helper.
- **A DB-backed page needs `export const dynamic = "force-dynamic"` or Next bakes it into a static snapshot at build time.** Discovered when Dashboard/Analytics/Reading/Timeline/Notes first came back as `○ (Static)` in `npm run build` output after being made `async` — they had no dynamic API (cookies/headers/searchParams) forcing dynamic rendering, so Next happily prerendered them once against whatever was in Neon during the build and would have served that frozen snapshot on every request after deploy. Every other DB-backed page (Library, Collections, etc.) already had this export; it was just missed for the newest five until caught by checking the build route table, not just `tsc`.
- **`components/home/animated-counter.tsx`'s count-up (`useInView` + `motion/react`'s `animate()`, both RAF-driven) never advances in the Browser-pane preview tool** — stat tiles render stuck at their initial `0` there even though the real numbers are correctly embedded in the server-rendered HTML (confirmed via `curl`). Same root cause as the Suspense-streaming gotcha below: don't treat a frozen `AnimatedCounter` in this tool as a real bug — check the HTML/RSC payload directly, or just trust it renders correctly in a real browser (it does — Playwright/manual testing would show the animation complete).
- **This machine's `gh` CLI has two cached GitHub accounts** (`dhanu-af`, `khdanushka-spec`), only one active at a time. Before any push here: `gh auth status` to check, `gh auth switch --hostname github.com --user khdanushka-spec` before pushing, then switch back to `dhanu-af` afterward so Dhanu's other projects on this machine aren't disrupted.
- **Real outbound DB connections work fine from the Bash tool on this machine** — `prisma migrate dev` / `db seed` ran successfully against the live Neon database. (An older cross-project memory claiming otherwise was specific to a different context and has been corrected.)
- **The Browser-pane preview tool can fail to visually show server-streamed Suspense content even when the server response is genuinely correct** — confirmed by `fetch()`ing a page directly and finding the right HTML sitting in a hidden `<div id="S:*">` that never got swapped into view (same root cause as a known "RAF never fires in this tool" limitation). If a page looks stuck/blank here despite clean server logs, `fetch()` it directly before assuming a real bug — and consider whether the `<Suspense>` boundary causing it is even still needed.
- `npx vercel integration add neon --claim --environment production --environment preview --environment development` provisions a real Neon DB via the Vercel Marketplace, connects it to the project, and writes credentials to `.env.local` (gitignored) in one command.
- Windows: stop the local dev server before running `prisma generate`/`migrate` (file lock on the query engine `.dll.node`).
- `dotenv` prints a rotating promotional "tip" line on every `config()` call (once referenced `www.vestauth.com`) — cosmetic, not a security concern.
- **The Neon serverless driver (`@neondatabase/serverless` + `ws` adapter) occasionally throws a transient `ETIMEDOUT`/connection error under `next dev`** when several routes fetch concurrently (rapid navigation, HMR reconnects, a Server Action landing mid-navigation) — surfaced twice now as a page 500 with the identical digest `2829966751@E394` and a browser-console `Uncaught Error: {clientVersion: "7.9.1"}`, both times immediately after a burst of page loads plus a Server Action call, both times resolved by an immediate reload. Treat an isolated transient 500 from a DB page as this, not a real regression — but the repeat occurrence (once during the Dashboard migration session, once during Edit/Delete verification) means it's a real recurring characteristic of this dev setup, not a one-off. If it ever blocks verification and a reload doesn't clear it, worth revisiting the Prisma singleton in `lib/prisma.ts` (e.g. connection retry/backoff) rather than continuing to treat it as always-transient.
