# Handover — 2026-08-10

## Goal
Dhanu asked to build "LuxLibrary OS" — a premium personal-library operating system for a 2,000+ book collector, from an extensive spec (11-phase build: dashboard, catalog, AI librarian, collections, analytics, reading tracker, etc.). Work proceeded: marketing home page first, then "the Operation site" (the actual app), then iteratively via bare "next" / "next 5" prompts to build out the full IA one module (or batch) at a time, then "confirm and do it" to provision a real database and migrate pages off mock data one at a time, then finished that migration, then made Add Book actually persist, then added book edit/delete, then built the Profile page (all same day, across several back-to-back sessions).

## State
- Marketing site (`/`) and the full app shell (sidebar covering every IA section, topbar with search + Add Book) are built and deployed.
- **All 21 screens are now built.** Profile (the last one) is real, DB-derived stats — not a placeholder. `app/(os)/[section]/page.tsx`'s generic "not built yet" fallback is now genuinely unreachable from the sidebar/footer nav (every `NavItem` in `lib/nav.ts` has a real page), though the route itself is still there for any future nav item added without a page yet.
- **A real Neon Postgres database is live and seeded**: 28 books, 18 authors, 8 publishers, 7 genres, 2 series, 7 shelves, 6 notes, 13 quotes — the same content the mock data always showed, now persisted for real.
- **Every screen now reads from the real database.** `lib/mock-data.ts`'s `MOCK_BOOKS` and `MOCK_NOTES` are no longer imported by any page — only by `prisma/seed.ts`. This session migrated the last five: Dashboard, Analytics, Reading Life, Timeline, Notes.
- No auth (single-owner app, deliberately not built).
- **Add Book, Edit, and Delete all actually persist now, with a near-complete catalog-field set.** Add creates a real `Book` row (plus `Author`/`Genre`/`Publisher`/`Series` upserts); Edit (on Book Detail) updates title/author/genre/format/status/rating/publisher/isbn13/pages/year/purchasePrice/series/seriesVolume/condition/language/personalReview/personalNotes/purchaseDate/purchaseSeller/currentMarketValue/insuranceValue; Delete (two-step confirm on Book Detail) removes the row and redirects to Library. All three live in `lib/book-actions.ts` and revalidate the whole app. Only `readingSessions` and cover-image fields remain unwired.
- **CSV bulk import is live** at `/library/import` (linked from the Library page header) — paste or upload a CSV, download a sample template, get a per-row created/updated/skipped summary. A row whose `isbn13` matches a book already in the library updates it in place instead of creating a duplicate.
- **Reading progress and dates are now really tracked.** Moving a book to "reading" (via Add or Edit) opens a real `ReadingSession`; moving it away closes the session; moving to "completed" sets `readingProgressPercent` to 100 automatically. Dashboard/Reading Life read this real data when it exists and fall back to the old `hashCode()`-derived placeholder only for books that have never gone through a real transition (the original 4 "reading" / 13 "completed" seeded books). No real LLM behind AI Librarian (rule-based pattern matching over real data, clearly labeled as such in the UI, not hidden as if it were a live model).
- Production: **https://luxlibrary-os.vercel.app** — Vercel project `dkns/luxlibrary-os`, auto-deploys on push to `master`. GitHub: `khdanushka-spec/luxlibrary-os` (public).

## Key decisions
- **Mock data first, database later, page by page.** Every module was built against a shared `lib/mock-data.ts` dataset before any database existed, then migrated to Prisma incrementally (Library+Detail together, then 6 aggregation pages, then Quotes+Search, then AI Librarian, then Dashboard/Analytics/Reading Life/Timeline/Notes — the last batch) rather than provisioning a DB up front or converting everything at once. Every intermediate state stayed shippable, and each migration step was verified against numbers already known from the mock-data era — a real bug (see Gotchas) was caught this way.
- **Dashboard's "curated" content (today's pick, AI insights, favorite genres/authors) is now computed live from real book data, not fixed mock strings** — new `lib/dashboard.ts` (`getTodaysPick`, `getAiInsights`), plus new aggregate queries in `lib/db-books.ts` (`getDashboardStatsFromDb`, `getCollectionValueFromDb`, `getRecentlyAddedFromDb`, `getTopGenresFromDb`, `getTopAuthorsFromDb`, `getNotesFromDb`). Same rule-based-but-real philosophy as AI Librarian. `lib/analytics.ts`'s `getAnalytics()` now takes `(books, totalValue, avgValue)` — the value figures come from a real `purchasePrice` Prisma aggregate instead of `getBookDetail()`, closing the Analytics gotcha called out in the previous handover. `lib/reading.ts` and `lib/timeline.ts` now take `books`/`notes` as parameters instead of importing mock data directly, following the pattern `lib/collections.ts`/`lib/publishers.ts` already used. Reading streak (`MOCK_STATS.readingStreakDays`) stays mock-sourced deliberately — there's no `ReadingSession` data to derive a real streak from.
- **New DB-backed pages must set `export const dynamic = "force-dynamic"`** or Next statically renders them once at build time using whatever was in the database during `next build`, then never refreshes — caught when a first build showed Dashboard/Analytics/Reading/Timeline/Notes as `○ (Static)` instead of `ƒ (Dynamic)` like every other DB page. All five now have it.
- **All three book mutations (`lib/book-actions.ts`'s `addBook`/`updateBook`/`deleteBook`) call `revalidatePath("/", "layout")`** rather than listing every individual route that shows book counts (Library, Dashboard, Analytics, Wishlist, Authors, Genres, Reading, Collections...) — simpler and correct for a single-owner app with no meaningful traffic cost to a full-app revalidation. The Add Book dialog's genre/format/status `<select>`s were previously uncontrolled (no `value`/`onChange`) and silently ignored on submit even during the mock-only era — now controlled state, actually sent to the action.
- **Editing a book's author/genre re-links via delete-then-recreate, not update-in-place.** `updateBook` deletes the book's existing `BookContributor`/`BookGenre` rows, then creates fresh ones against the (possibly new, possibly upserted-existing) author/genre — needed because those are composite-PK join rows keyed on the old author/genre id, not a field that can be reassigned. Renaming an author this way does **not** clean up the old `Author`/`Genre` row if it's now orphaned (0 books) — left as-is deliberately, since every page that lists authors/genres derives its list from `getAllBooksFromDb()`'s book-author relations, not the `Author`/`Genre` tables directly, so an orphaned row is invisible everywhere in the UI and costs nothing to leave.
- **Delete uses a two-click same-button confirm** (`components/library/delete-book-button.tsx`: "Delete" → click → "Confirm delete?" → click → deletes), not a separate modal, and resets back to the unarmed state on blur — no `window.confirm()` (blocks the event loop and looks out of place in this UI) and no extra dialog component for a single destructive action.
- **Edit's initial field values must come from the raw underlying field, not a display-fallback field.** `getBookDetailFromDb` returns both `book.publisher` (raw, `undefined` if unset) and `publisher` (the same value with `?? "Unknown"` applied for display). `EditBookDialog` is fed `book.publisher`, not `detail.publisher` — feeding it the display value would mean editing any book with no real publisher literally saves a `Publisher` row named "Unknown". The same shape trap applies to any other field that has a display fallback elsewhere in the app; check for one before wiring a new prop into an edit form.
- **`isbn13` is `@unique` on `Book`** — `addBook`/`updateBook` catch the Prisma `P2002` unique-constraint error code and return a friendly `"That ISBN is already in your library."` instead of letting an unhandled exception surface. A blank ISBN is sent as `undefined` (create) / `null` (update), never `""` — an empty string would collide across every book with a blank ISBN under the unique constraint.
- **The Browser pane's accessibility-tree label for an `<input>` falls back to `placeholder` even when the input has a real, non-empty `value`** — an Edit dialog field that was actually correctly pre-filled looked empty in `read_page`'s output (showed the placeholder text as the field's name) until checked via `document.querySelector(...).value` directly. If a pre-filled/controlled input looks wrong in this tool's accessibility tree, verify the actual DOM `.value` with `javascript_tool` before concluding there's a real bug.
- **Series/volume followed the exact publisher pattern**: `resolveSeriesId()` in `lib/book-actions.ts` mirrors `resolvePublisherId()` — upsert-by-name, return the id or `null`. Also surfaced a small pre-existing gap while wiring this up: Book Detail's "Details" section never displayed series/volume at all, even for the two seeded series (Hainish Cycle, Earthsea Cycle) — added a "Series" row there too, not just made the field editable.
- **Condition/language went into both Add and Edit (cataloging-time fields); review/notes/purchase provenance went into Edit only** — deliberately not Add, since you don't have a review or purchase history for a book you're adding right this second. `getBookDetailFromDb` now also returns `rawCondition`/`rawLanguage` alongside the existing display-formatted `condition`/`language` (which apply `?? "English"` etc.) — Edit is fed the raw ones, following the exact lesson from the publisher bug two sessions ago.
- **A `"use server"` file can only export async functions** — hit this building the CSV importer: `lib/book-actions.ts`'s sync `isUniqueConstraintError()` helper couldn't be exported from that file once `lib/import-actions.ts` needed to reuse it, so it moved to a new non-server `lib/prisma-errors.ts`. `resolvePublisherId`/`resolveSeriesId` stayed in `book-actions.ts` and got exported instead, since they're already `async`.
- **CSV import processes rows sequentially, not via `Promise.all`** — deliberately, so a duplicate ISBN or bad row fails just that row (caught per-row, reported with a reason) instead of racing concurrent upserts of the same author/genre/publisher across rows or aborting the whole batch on the first error. `lib/csv.ts` is a plain pure-function parser (hand-rolled, handles quoted/escaped fields) with no server directive, so nothing stops it from being reused client-side later (e.g. a live preview before import) even though the current UI doesn't do that yet.
- **Real reading-session tracking reuses the existing `hashCode()` fallback pattern rather than backfilling seed data.** `Book.readingProgressPercent` and the `ReadingSession` model existed in the schema since the start but were never written to — `updateBook`/`addBook` now create/close a session on every status transition into/out of "reading", and `lib/reading.ts` prefers that real data (`book.readingProgressPercent`, `book.readingStartedAt`/`completedAt`) but falls back to the old hash-derived numbers when a book has neither (i.e. was never edited since this feature shipped). This means the 4 originally-"reading" and 13 originally-"completed" seeded books keep showing their exact pre-existing numbers forever unless Dhanu actually edits them — verified this holds (zero visible change) before and after the change, rather than assuming it. `getCompletedThisYear()` also now discards a real `completedAt` from a past year, a case the always-current-year hash fallback never needed to handle.
- **A new mutation path has to replicate session-tracking, not just the field write.** CSV import (`bulkImportBooks`) bypasses `addBook`/`updateBook` entirely (direct `prisma.book.create`/`update`), so when it went in it silently didn't open/close `ReadingSession`s the way the dialogs do — caught by testing the exact "set status to Reading via CSV" path right after building it, not by inspection. Fixed by duplicating the same transition-check logic into both `bulkImportBooks` branches. **Any future third way to write a book's `readingStatus` needs this too** — it isn't enforced by the schema or a shared helper, just convention.
- **Profile has no real per-user data model to back it** (single-owner app, no `User`/`Account` table) — rather than fabricate fake editable-but-non-persisting name/bio fields (which would be misleading in a way Settings' toggles aren't, since typing a name and having it vanish on refresh reads as broken, not "preview"), Profile is entirely real, DB-derived aggregate stats (reusing the same `lib/db-books.ts`/`lib/reading.ts` functions Dashboard and Analytics already use) plus the static `MOCK_OWNER_NAME`/`MOCK_STATS.readingStreakDays` the rest of the app already treats as given constants, not user input.
- **Migrating a page to the database means adapting Prisma rows into the existing `MockBook` shape** (`lib/db-books.ts`'s `toMockBook()`), not rewriting consuming components — `BookCard`, `BookListRow`, `LibraryView`, etc. never changed; only what a page fetched from did.
- **Library and Book Detail were migrated together, not one at a time**, because they're linked by id — wiring one to real DB ids while the other still looked up the old mock "1".."28" ids would have made every click-through 404.
- **shadcn/ui here is built on Base UI, not Radix.** Components take a `render` prop instead of `asChild` (e.g. `<Button render={<a href="/x" />}>`), and a non-`<button>` render target needs `nativeButton={false}` or Base UI logs a console error.
- **Prisma 7 moved connection config out of `schema.prisma`** into `prisma.config.ts`, and `PrismaClient` now requires an explicit driver `adapter` (`@prisma/adapter-neon` here) — a real API break from what most training data assumes. `prisma.config.ts` reads `process.env.DATABASE_URL` directly, not the throwing `env()` helper, so `prisma generate` survives a build before any database exists.

## Gotchas / constraints learned
- **The single biggest recurring bug class in this build**: `lib/book-detail.ts`'s `getBookDetail(book)` derives publisher/shelf/ISBN/summary/favorite-quote/purchasePrice from a hash of `book.id`. Fine for `MOCK_BOOKS` (stable "1".."28" ids), **silently wrong** for a database book (a real cuid the hash was never seeded against). Publishers (twice — see below), Quotes, Search, AI Librarian, and Analytics all hit this and needed a real fix — query the actually-stored field — not just a data-source swap. **Confirmed via a full grep audit that `getBookDetail()` is now called nowhere outside `prisma/seed.ts`** — but the previous handover claimed this a session early: `lib/publishers.ts`'s `publisherOf()` was still calling it as a fallback for any book with no `publisher` field (every book added through Add Book, since that form doesn't collect a publisher), silently inventing a fake publisher name for every one of them. Fixed to fall back to `"Unknown"` instead, matching the Book Detail page's existing pattern. **Lesson: verify a "this is now fully migrated" claim with a grep before trusting it in a future session** — a fallback branch is easy to miss when auditing by feature/page rather than by call site.
- **A DB-backed page needs `export const dynamic = "force-dynamic"` or Next bakes it into a static snapshot at build time.** Discovered when Dashboard/Analytics/Reading/Timeline/Notes first came back as `○ (Static)` in `npm run build` output after being made `async` — they had no dynamic API (cookies/headers/searchParams) forcing dynamic rendering, so Next happily prerendered them once against whatever was in Neon during the build and would have served that frozen snapshot on every request after deploy. Every other DB-backed page (Library, Collections, etc.) already had this export; it was just missed for the newest five until caught by checking the build route table, not just `tsc`.
- **`components/home/animated-counter.tsx`'s count-up (`useInView` + `motion/react`'s `animate()`, both RAF-driven) never advances in the Browser-pane preview tool** — stat tiles render stuck at their initial `0` there even though the real numbers are correctly embedded in the server-rendered HTML (confirmed via `curl`). Same root cause as the Suspense-streaming gotcha below: don't treat a frozen `AnimatedCounter` in this tool as a real bug — check the HTML/RSC payload directly, or just trust it renders correctly in a real browser (it does — Playwright/manual testing would show the animation complete).
- **This machine's `gh` CLI has two cached GitHub accounts** (`dhanu-af`, `khdanushka-spec`), only one active at a time. Before any push here: `gh auth status` to check, `gh auth switch --hostname github.com --user khdanushka-spec` before pushing, then switch back to `dhanu-af` afterward so Dhanu's other projects on this machine aren't disrupted.
- **Real outbound DB connections work fine from the Bash tool on this machine** — `prisma migrate dev` / `db seed` ran successfully against the live Neon database. (An older cross-project memory claiming otherwise was specific to a different context and has been corrected.)
- **The Browser-pane preview tool can fail to visually show server-streamed Suspense content even when the server response is genuinely correct** — confirmed by `fetch()`ing a page directly and finding the right HTML sitting in a hidden `<div id="S:*">` that never got swapped into view (same root cause as a known "RAF never fires in this tool" limitation). If a page looks stuck/blank here despite clean server logs, `fetch()` it directly before assuming a real bug — and consider whether the `<Suspense>` boundary causing it is even still needed.
- `npx vercel integration add neon --claim --environment production --environment preview --environment development` provisions a real Neon DB via the Vercel Marketplace, connects it to the project, and writes credentials to `.env.local` (gitignored) in one command.
- Windows: stop the local dev server before running `prisma generate`/`migrate` (file lock on the query engine `.dll.node`).
- `dotenv` prints a rotating promotional "tip" line on every `config()` call (once referenced `www.vestauth.com`) — cosmetic, not a security concern.
- **The Neon serverless driver (`@neondatabase/serverless` + `ws` adapter) throws a transient `ETIMEDOUT`/connection error under `next dev`** — a page 500 with the identical digest `2829966751@E394` and browser-console `Uncaught Error: {clientVersion: "7.9.1"}`. Happened four times across this and the prior session (Dashboard once, Library once during Edit/Delete verification, Profile **twice in a row** on first compile of that new route) — reliably tied to a route's *first* request after a dev-server (re)start or a brand-new route's first Turbopack compile, not random. Every occurrence was confirmed a false alarm by re-running the exact same DB calls in a standalone `tsx` script (always succeeded) and by reloading the page (succeeded within 1-3 reloads every time). **Do not debug application code in response to this** — reload first, and only suspect real application logic if a fresh route still fails after 3+ reloads with the dev server otherwise idle.

## Next steps
1. Cover-image fields (`coverImageUrl`/`backCoverImageUrl`/`spineImageUrl`/`galleryImageUrls`) are the last unwired `Book` columns — they need actual file upload/storage (Vercel Blob or similar), not just a form field, so they're a real infra decision, deliberately not done unprompted this session.
2. `ReadingSession` only tracks `startedAt`/`endedAt` automatically on status transitions — `minutesRead`/`pagesRead` per-session and multiple sessions per book (pause/resume with a gap) aren't captured; a book that goes reading → unread → reading again just gets two separate session rows with no UI to see the first one. Fine for the "one continuous read" case this was built for.
3. CSV import's merge-by-ISBN still has no duplicate-detection beyond the unique constraint — two rows in the same file with different or blank ISBNs for what's actually the same book both import as separate books, and merging by title+author fuzzy-match was deliberately not attempted (too failure-prone without a UI to review/confirm matches first).
4. Every screen in the spec IA exists, every core CRUD action is real with a full catalog-field set, reading progress/dates are really tracked, and CSV import now merges by ISBN instead of only creating. The only remaining gap that needs new infrastructure (not just more logic) is cover images. This is a strong check-in point with Dhanu — most of what's left is either infra (image storage, auth) or genuinely optional polish.
