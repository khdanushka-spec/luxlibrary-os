## Key decisions
- **Consolidated the spec's suggested schema.** The user's request listed `MessageReply/reference`, `MessageBookShare`, and `BannedMember` as possibly-separate models. Implemented instead as: `replyToId`/`forwardedFromId` self-relations on `CommunityMessage` (simpler, matches this codebase's existing self-relation patterns), `sharedBookId` as a direct nullable FK to `Book` on `CommunityMessage` with a `type` enum (`TEXT`/`POLL`/`BOOK_SHARE`) distinguishing message kinds, and a `CommunityMemberStatus` enum (`ACTIVE`/`LEFT`/`REMOVED`/`BANNED`) instead of a separate ban table. Fewer models, same capability.
- **No separate `MessageMention` table.** `@mention` is purely client-side: the composer's autocomplete inserts literal `@Name ` text, and the renderer highlights any `@Name` substring that matches a current member's name via regex. No structured "who was mentioned" data is persisted — there's no mention-notification feature requested, so this was enough.
- **Admin = the existing `User.role === "SUPER_ADMIN"`.** No per-community admin-assignment system — reuses the site's existing single global admin role directly, per the user's explicit "reuse existing auth" instruction and "don't over-engineer."
- **"Read/unread indicators" implemented as unread-count + a single fixed "New messages" divider**, not per-message read receipts (no `MessageRead` join table). A full read-receipt fan-out (who's seen which message) was judged out of scope for a v1 WhatsApp-*style* text chat.
- **Presence ("online") and typing are polling-derived, not a websocket.** No realtime infra exists in this project. `CommunityMember.lastSeenAt` is bumped on every poll tick (4s interval) and on send; "online" = seen within the last 45s. `CommunityMember.typingUntil` is bumped (throttled to once per 3s while actively typing) and expires after 6s. This is genuinely good enough in testing — messages/reactions/deletes from Dhanu's parallel real session showed up within one poll cycle.
- **Deleted messages are soft-deleted** (`isDeleted` flag + `deletedById`/`deletedAt`), not hard-deleted — matches WhatsApp's "This message was deleted" placeholder UX and preserves an audit trail for admin moderation.
- **Book-share privacy required relaxing the Book Detail page's ownership gate** (`app/(os)/library/[id]/page.tsx`) — previously `notFound()` unless `detail.userId === user.id || user.role === "SUPER_ADMIN"`. Now also allows viewing (not managing) if `wasBookSharedWithMember(bookId, viewerId)` is true (an active community member, and the book was shared in a non-deleted community message). A `canManage` boolean gates every management control (Edit/Delete book, shelf location, purchase/financial fields, Notes section entirely, Quotes add/edit/delete) so a shared-view visitor gets a real but reduced read view, never write access or private financial/location data. This is the one place this session touched a *pre-existing* page rather than purely adding new files — deliberate, reviewed carefully, not a redesign.
- **`prisma.communityMessage.findMany({ orderBy: "asc", take: limit })` was a real correctness bug**, not just a style nit — with ascending order, `take` returns the *oldest* N messages, not the most recent. Fixed to query `desc` + `take` + `.reverse()` in JS. Only matters once a community exceeds the 300-message cap, but worth knowing it was caught and fixed, not just theoretical.

## Gotchas / constraints learned this session (in addition to everything in git history's older HANDOVER.md revisions, still valid)
- **`.env.local`'s `DATABASE_URL` points at the real/shared Neon database, not an isolated dev branch.** Every test account, message, and admin action this session happened against the same database real users (`khdanushka@gmail.com`, `dnanduni@gmail.com`) can see. This was already true in earlier parts of this session (confirmed by seeing "Nanduni" in the admin panel earlier) but is *especially* consequential for a chat feature, since real accounts can watch test messages appear live. Treat every local `npm run dev` session as touching production data.
- **Two real concurrency bugs were found and fixed** in code that runs on *every single page load* (the `(os)` layout calls `ensureMembership`/`getOrCreateCommunity` unconditionally):
  1. `ensureMembership` was `findUnique`-then-`create` — under concurrent requests (very plausible here, since the layout fires on every navigation and two people/tabs can easily overlap), this raced on the `@@unique([communityId, userId])` constraint and threw an unhandled `PrismaClientKnownRequestError`, crashing the whole page. **Fixed with `upsert` on that same unique key.**
  2. `getOrCreateCommunity` was `findFirst`-then-`create` with *no unique key to upsert on at all* — this actually created **3 duplicate `Community` rows** within ~700ms during this session's testing (all requests raced simultaneously right after the first test account was created). **Fixed by adding `Community.singletonKey` (`@unique @default("bringbooks-community")`) and upserting on it** — migration `20260810131700_community_singleton_key`.
  - **Because of bug #2, my own testing accidentally called `adminRemoveMember` on `khdanushka@gmail.com`'s real account** (she was, at that moment, the only other member — I hadn't created the throwaway regular-member account yet, and mis-clicked what I intended to be a test target). This was caught immediately by checking a diagnostic dump, and her membership was manually restored to `ACTIVE`. **Verify this again in the next session** — check `khdanushka@gmail.com`'s `CommunityMember.status` is `ACTIVE` before anything else, via the members panel or a quick Prisma query. The 2 empty duplicate `Community` rows from bug #2 were deleted; the real one (7 messages, all test history) was kept.
  - `toggleReaction`/`toggleStar` still use a `findUnique`-then-`create`/`delete` pattern, *not* upserted — left as-is because they're triggered by an explicit single user click (not an unconditional per-page-load path like the two bugs above), so the race window is far narrower. Worth revisiting if it ever actually manifests, but not urgent.
- **A live poll-vote bug**: `CommunityMessageView.poll` never included the actual `Poll.id` — only `question`/`totalVotes`/`myOptionId`/`options`. The UI was accidentally passing the *CommunityMessage's* id as the poll id when voting, which the server correctly rejected (`option.pollId !== pollId`) but the client's `refreshAfter` helper doesn't surface action errors, so votes silently no-opped. **Fixed**: added `poll.id` to the type/mapper (`lib/community.ts`) and fixed the call site in `components/community/message-bubble.tsx`'s `PollCard` (`onVote(message.poll!.id, optionId)` instead of `onVote(message.id, optionId)`). Confirmed fixed by voting and seeing percentages update.
- **`refreshAfter` in `community-view.tsx` doesn't check `result.ok`** on the "quick" actions (react/pin/star/forward/delete/vote) — it just awaits the action and refetches. This masked the poll bug above (a clean `{ok:false}` still refetches with no visible error). No user-facing error surfaces if one of these ever legitimately fails. Acceptable for v1 since these paths are guarded by UI visibility (you can't click Pin unless you're rendered as admin), but worth knowing if something "silently doesn't work" later — check server logs, the client won't tell you.
- **A throwaway diagnostic login route is still in the tree**: `app/api/dev-login-test/route.ts` — `GET /api/dev-login-test?email=X` logs in as `X` with the fixed password `TestPass123!` (only works for accounts actually created with that password this session, not a real bypass, but still delete it before ever committing/pushing). Also created and already deleted this session: `app/api/dev-check`, `app/api/dev-cleanup`, `app/api/dev-logout` — none of those remain, only `dev-login-test` is still present.
- **Restarting the dev server is required after any `prisma migrate` / `prisma generate`** — the running Next dev process holds a stale Prisma Client in memory and throws `Unknown argument` errors otherwise (bit twice this session before remembering; documented in an earlier HANDOVER too).
- **`prisma migrate dev` cannot run in this non-interactive shell** when it detects a warning worth confirming (e.g., "unique constraint... will fail if duplicates exist") — it errors with "environment is non-interactive." Workaround used successfully: hand-write the migration folder/SQL matching Prisma's naming convention (`YYYYMMDDHHMMSS_name/migration.sql`), then apply with `npx prisma migrate deploy` (non-interactive, no prompts). Used for the singleton-key migration.
- **Real-browser click automation on this project intermittently fails to trigger onClick** for reasons unrelated to the code (established in earlier sessions too) — `element.click()` via the JS tool works reliably; `computer` tool coordinate clicks sometimes silently don't register. When testing anything here, prefer `javascript_tool` dispatching real `.click()` calls, and when chaining a dropdown-open-then-click-inside sequence, do both steps inside **one** `javascript_exec` call with a short `await new Promise(r => setTimeout(r, 200-300))` between them — doing them as two separate tool calls sometimes loses focus/selection state (bit the @mention-insert test and the admin-remove-member test both this way before switching to atomic single-script actions).
